## 1. 這個 checkpoint 要回答的問題

> **只靠棋子與色塊，玩家會不會因為情報（掃描、未確認接觸、假接觸）而改變部署？**

CP1 刻意不做 3D、不做美術、不做研發。若在最陽春的呈現下情報機制就沒人在意，後面的雙尺度渲染再漂亮也救不了——這正是 ADR-0001 的重新評估條件 1。

## 3. 灰盒地圖：Crossroads-6

6 個戰場區＋2 個 HQ 區，點對稱。`—` 為縱向連通，`═` 為橫向換側通道。

```
            [B-HQ]
           /      \
       [B-L] ═══ [B-R]          B-R：B 方前哨
         |          |
   ◆ [Mid-L] ═══ [Mid-R] ◆       ◆＝補給節點
         |          |
       [A-L] ═══ [A-R]          A-L：A 方前哨
           \      /
            [A-HQ]
```

| 項目 | 預設 |
|---|---|
| 相鄰區移動時間 | 縱向 8 秒、橫向換側 12 秒（偵察 ×0.75，裝甲 ×1.0，步兵 ×1.25，火砲 ×1.5） |
| 補給節點 | 開局中立。區內只有單一方的作戰單位（不含移動中單位）持續 10 秒即易手；雙方同在時進度凍結；區內無人或占領方換邊時進度歸零 |
| 前哨 | HP 400；首次被摧毀給攻方 +50（一次性，事件去重） |
| HQ | HP 1500；歸零即終局 |

## 4. 規則預設值

### 4.1 經濟與排產

| 規則 | 預設 |
|---|---|
| 起始補給 | 120 |
| 收入 | 基礎每 10 秒 +10；每控制 1 個補給節點每 10 秒 +8 |
| 單位 | 步兵 30／5s、偵察 45／6s、裝甲 70／10s、火砲 85／12s |
| 佇列 | 共用 1 條，上限 3 筆訂單（**含**生產中的那一筆）；下單即扣費 |
| 取消 | 任何訂單都可取消，全額退費並立即釋放人口；後面的訂單從頭開始計時 |
| 人口上限 | 每方 30（計入排隊與存活） |
| 出生點 | 己方 HQ 區 |

### 4.2 移動與交戰（區域制，無精確彈道）

**移動**

- 移動中的單位在抵達前仍屬於出發區：可被看見、可被攻擊、會還擊，但不計入占點。抵達那個 tick 才換區。
- 新的移動指令取消現行路線，從目前所屬區重算最短路徑（依移動時間，平手取區域 ID 字典序較小者）。
- `hold`：停止移動，原地自動交戰。
- `retreat`：移動到移動時間最短的己方 HQ 或己方控制節點（平手取區域 ID 較小者）；沒有目標就視同 `hold`。

**交戰**

- 每秒（每 10 tick）結算一次；所有攻擊者先選目標、彙總傷害，再同時扣血（同 tick 互殺成立）。
- 射程：步兵、偵察、裝甲只攻擊同區；火砲攻擊同區，或相鄰區中對己方為「已確認」的目標。攻擊未確認接觸無效。
- 目標選擇：**先打敵方單位，射程內沒有單位才打建築**（前哨、HQ）。同類目標依「克制優先 → 最低 HP → 最小 `entityId`」穩定排序。
- 整數運算：HP 與傷害內部以 **1/10 點**為單位儲存（顯示時再除以 10）；倍率以整數分數表示（×1.5＝×3/2，先乘後除、無條件捨去）。

| 單位 | HP | 每秒傷害 | 克制 | 視野 |
|---|---|---|---|---|
| 步兵 | 100 | 10 | 對火砲 ×1.5 | 本區 |
| 偵察 | 60 | 5 | — | 本區＋相鄰區 |
| 裝甲 | 260 | 18 | 對步兵 ×1.5 | 本區 |
| 火砲 | 80 | 22 | 對建築 ×1.5 | 本區 |

### 4.3 情報層（CP1 的核心）

每個敵方實體對某一方只會是下列四種之一，由 `buildPlayerView(world, side)` 計算；條件重疊時依表格由上而下取第一個成立的狀態。

| 優先 | 狀態 | 何時成立 | `PlayerView` 透露什麼 |
|---|---|---|---|
| 1 | 已確認單位 | 在己方單位同區、偵察視野內、或掃描生效中 | 兵種、HP 百分比、所在區 |
| 2 | 未確認接觸 | 位於「己方單位所在區的相鄰區」但不符合已確認 | 併入該區的接觸群（見下） |
| 3 | 最後已知位置 | 曾為已確認，之後離開視野 | 最後區域＋時間戳；30 秒後淡出 |
| 4 | 不可見 | 以上皆非 | 什麼都沒有 |

**接觸群**

- 真實未確認接觸以「區」為單位聚合：一個區對一方最多一個真實接觸群，顯示粗略規模——1–2 個實體為小、3–5 個為中、6 個以上為大。不含兵種、HP、真實 `entityId`。
- 接觸群使用每方獨立的 contact ID（不得等於或推導出真實 `entityId`）；接觸群消失後再出現就換新 ID。
- 假接觸是獨立的一筆接觸，固定顯示為「中」，與同區的真實接觸群並列。

**標記清理**

- 實體重新被確認時，移除它的最後已知位置標記。
- 掃描一個區時，清除掃描方在該區的所有最後已知位置標記，改以掃描結果為準。

**掃描**：費用 20、冷卻 45 秒；對指定區揭露 10 秒。揭露期間區內真實單位變「已確認」；區內的假接觸**只在掃描方畫面**上標示「無實體」2 秒後移除（放置方不會得知被識破）。

**假接觸**：費用 15、冷卻 30 秒、每方同時最多 2 個、存活 40 秒。放在任一己方曾見過的區。不造成傷害、不占點、不擋路、不計入擊毀統計、不給補給。

**結算揭露**：對局結束後，雙方都看得到完整的假接觸紀錄（誰、何時、何處、是否被掃描識破、是否調動對手）。

### 4.4 指令、暫停與終局

- 指令：`move(zone)`、`hold`、`retreat`、`produce(unitType)`、`cancel(orderId)`、`scan(zone)`、`decoy(zone)`、`pause`／`resume`（單機）。
- 處理順序：每 tick 開頭依 `(tick, side, seq)` 穩定排序後套用。`seq` 重複、目標不存在、費用或冷卻不足等非法指令一律拒絕並發出帶原因的 `commandRejected`。
- 暫停：`pause`／`resume` 是單機的控制指令，由前端的遊戲迴圈處理，**不進入模擬指令佇列**、也不推進 tick。暫停期間送出的遊戲指令排入下一個 tick，恢復後依序生效。
- 終局：任一 HQ 歸零即結束；同 tick 雙 HQ 歸零判平局。第 7200 tick（12 分鐘）先完成該 tick 的傷害與 HQ 判定，仍未分出勝負才做超時判定：HQ 血量百分比 → 控制節點數 → 平局。終局後拒收指令。

### 4.5 最小 AI（AI v0）

- 只接收自己的 `PlayerView`；型別上就拿不到 `WorldState`。每 2 秒決策一次，使用自己的種子 RNG。
- 部隊調度每次只執行第一條成立的規則：
  1. **防守**：己方 HQ、前哨或已控節點所在區或其相鄰區出現接觸時：
     - 掃描可用 → 先掃描該區；掃描結果為空（或只有假接觸）就不派兵。
     - 掃描不可用 → 依估計強度派兵。估計：小＝2、中＝4、大＝7 個步兵當量（裝甲＝2、火砲＝1、偵察＝0.5 個當量）；派出當量 ≥ 估計＋1，由近到遠、同距離取 `entityId` 小者。**這是假接觸能調動 AI 的來源。**
  2. **進攻**：已控 2 個節點且兵力 ≥ 12 個當量時，往敵方 HQ 推進。
  3. **擴張**：把閒置單位推向最近的未控補給節點。
- 與部隊調度獨立執行：
  - **假接觸**：每 90 秒至少嘗試放一次，放在離己方最近的敵控或中立節點。
  - **生產**：依 4:2:2:1（步兵：裝甲：偵察：火砲）補足，補給足夠時保持佇列滿檔。

### 4.6 事件契約（分析與結算的資料來源）

事件流同時供結算統計、回放測試與試玩分析使用。對局中 UI 與 AI 只能讀 `PlayerView`，**不得**讀事件流。

| 事件 | 主要欄位 |
|---|---|
| `commandAccepted`／`commandRejected` | tick、side、seq、commandId、kind、payload（目標區、兵種等）、reason（拒絕時） |
| `unitSpawned`／`unitDestroyed` | entityId、side、unitType、zone、killerSide |
| `unitMoved` | entityId、from、to、cause（`command`／`retreat`） |
| `nodeCaptured`、`outpostDestroyed`、`hqDamaged`、`matchEnded` | 對應 ID、side、結果與判定理由 |
| `contactAppeared`／`contactCleared` | viewerSide、contactId、zone、size、isDecoy、decoyOwnerSide（後兩者僅供事後分析） |
| `scanStarted`／`scanResolved` | side、zone、confirmedCount、decoysExposed |
| `decoyPlaced`／`decoyExpired`／`decoyExposed` | side、contactId、zone |

### CP1-01｜Monorepo 骨架與 PR CI

- npm workspaces：`packages/sim`、`packages/content`、`apps/web`、`fixtures/`；TypeScript strict、Vite、Vitest、ESLint、Prettier；`.nvmrc` 釘 Node 主版本。
- `npm run verify` = lint＋typecheck＋schema 檢查＋單元測試；`test:e2e` 先放可執行的空殼。
- `.github/workflows/ci.yml`：PR 與 push 到 `main` 時跑 `npm ci && npm run verify`；只用 GitHub-hosted runner。
- 一條 ESLint 規則或測試確保 `packages/sim` 不得 import DOM、`three`、`pixi.js`，也不得使用 `Date`、`performance`、`Math.random`。
- **驗收**：乾淨 checkout 執行 `npm ci && npm run verify` 通過；CI 在 PR 上綠燈；故意在 sim 加 `Math.random()` 會讓 verify 失敗。

### CP1-02｜內容 schema 與契約型別

- `packages/content`：單位、地圖（區、連通、移動時間、節點、前哨）、情報行動、AI 估算參數的 JSON＋JSON Schema，帶 `schemaVersion` 與 `rulesVersion`。
- `packages/sim/src/contracts.ts`：`Command`、`Event`（第 4.6 節全部事件）、`PlayerView`、`Replay`，以及可見性查詢介面 `Visibility`（`isConfirmed(side, entityId)`），讓 CP1-03 能以注入的替身測火砲射程，CP1-04 再接上真實實作。
- schema 驗證腳本：重複 ID、缺引用（連到不存在的區）、負值、未知欄位都要失敗。
- mock `PlayerView` 範例供前端使用。
- **驗收**：`fixtures/content/` 至少 1 份有效、4 份無效（各對應一種錯誤）資料，測試逐一驗證；Crossroads-6 以資料表表達、程式中無寫死地圖；`PlayerView` 型別沒有任何欄位能放敵方真實 `entityId`。

### CP1-03｜模擬核心

- `createWorld(content, seed)`、`step(world, commands, visibility) → { world, events }`，固定 10 Hz。
- 實作第 3、4.1、4.2、4.4 節規則，產生第 4.6 節中屬於模擬核心的事件；`deriveMatchStats(events)` 由事件流推導擊毀統計（以 `entityId` 去重）。
- **驗收**：
  - 決定性：100 組隨機種子＋隨機指令序列，各跑兩次，事件流雜湊完全相同。
  - 經濟：前哨獎勵在回放中不重複發放；下單扣費、取消退費與人口釋放的帳目測試。
  - 移動：移動中被攻擊、改令重算、`retreat` 無目標時視同 `hold`，各一個測試。
  - 交戰：先單位後建築；同 tick 互殺；1/10 點取整；火砲以替身 `Visibility` 測相鄰區射擊（替身回報已確認時命中、未確認時不攻擊）。
  - 暫停：暫停期間送出的指令在恢復後的下一個 tick 依序生效，tick 計數在暫停期間不變。
  - 終局：同 tick 雙 HQ 歸零判平局；第 7200 tick 先判 HQ 再判超時；超時三層判定各一個測試；終局後指令產生 `commandRejected`。

### CP1-04｜情報層

- 實作 `buildPlayerView(world, side)` 與真實 `Visibility`；依第 4.3 節產生四種狀態、接觸群、標記清理、掃描與假接觸。
- **驗收**：
  - 防作弊屬性測試：50 組種子 × 每一 tick，`PlayerView` 中不出現任何對該方未曝光實體的真實 `entityId`、兵種或 HP。
  - 接觸群：規模門檻（2／3、5／6 邊界）、真假同區並列、消失後重新出現換新 ID，各一個測試。
  - 狀態優先序：已確認敵軍退到相鄰區時顯示為未確認接觸，不重複出現最後已知位置標記。
  - 誘餌：零傷害、零占點、零擊毀計數、零補給（各一個測試）；被掃描時只有掃描方看到「無實體」。
  - 整合：以真實 `Visibility` 重跑 CP1-03 的火砲相鄰區測試。
  - fixture：至少 3 組「種子＋指令序列 → 預期 `PlayerView` 快照」。

### CP1-05｜AI v0

- 依第 4.5 節；AI 模組的函式簽名只接受 `PlayerView`（與自己的 RNG）並回傳 `Command[]`。
- **驗收**：
  - 型別層面無法取得 `WorldState`（測試或 lint 規則證明）。
  - 情境 A（掃描冷卻中）：在 AI 的 HQ 相鄰區放一個假接觸，10 秒內 AI 實際對該區下移動指令。
  - 情境 B（掃描可用）：同上，AI 先掃描，識破後不派兵。
  - AI 對 AI 50 局：每局在 7200 tick 內產生唯一終局，無例外、無卡死；報告 HQ 擊破率、超時率與局長分布（診斷用，不是門檻；真人局長門檻見第 6 節）。

### CP1-06｜2D 灰盒前端

- `apps/web`：只讀 `PlayerView`；SVG 或 Canvas 2D 畫區域圖、棋子（形狀區分兵種，不只靠顏色）、接觸群（問號＋規模）、最後已知位置（淡化＋秒數）。
- 操作：點選小隊或區內單位 → 點目標區＝移動；按鈕列提供固守、撤回、掃描、假接觸、生產、暫停。全程以 Pointer Events 實作，**不依賴 hover、右鍵或鍵盤**；觸控目標 ≥ 44 px。
- 頁面切到背景時自動暫停。結算頁：勝負、各兵種擊毀數（`deriveMatchStats`）、雙方假接觸紀錄、「下載事件紀錄（JSON）」按鈕。
- 把 `npm run test:e2e` 接進 PR CI。
- **驗收**：iPad Safari 與桌機 Chromium 各對 AI 完成一局（截圖或短錄影附在 PR；需 CP1-05 已合併）；`npm run test:e2e` 以 headless Chromium 跑「開局 → 下令 → 暫停 → 繼續 → 結算」smoke，並在 PR CI 綠燈。

### CP1-07｜試玩包與指標分析腳本

- `npm run build` 產出可直接以靜態檔託管的試玩版；版本頁顯示 commit 與 `rulesVersion`。
- 指標分析腳本（讀事件紀錄 JSON），規則：
  - **情報影響部署**：玩家方每次 `contactAppeared`（非自己放的）或 `scanResolved` 後 20 秒內，玩家首次 `commandAccepted`（kind＝`move`，payload 目標區為該區或其相鄰區）即配對一次；每個情報事件最多配對一次。這是訪談的交叉檢查，不是因果證明。
  - **欺敵有效**：AI 方的 `contactAppeared`（isDecoy＝true、decoyOwnerSide＝玩家）後 20 秒內，AI 的 `commandAccepted`（kind＝`move`，目標為該區或其相鄰區）即算一次（AI 的掃描不算）。沒使用假接觸的局不計入分母；分母為 0 記 `NOT MEASURED`。
  - **局長**：`matchEnded` 的 tick ÷ 600。
- 試玩紀錄表：對應第 5 節 CP1-08 的訪談題與觀察欄位、第 6 節的指標。
- **驗收**：分析腳本以 fixture 測試，fixture 同時包含應配對與不應配對（反例：跨兩區的移動、同一情報事件後的重複指令、AI 對真實接觸的調動）的情境；試玩版可在 iPad Safari 開啟並完成一局。

### CP1-08｜試玩執行與 CP1 gate

- 試玩流程：1 分鐘口頭說明（不給策略提示）→ 打 1–2 局 → 3 分鐘訪談：
  1. 「畫面上的問號是什麼？和實心棋子差在哪？」
  2. 「有沒有哪一次你因為看到（或掃描到）什麼而改變部隊位置？」
  3. 「你放過假接觸嗎？你覺得 AI 有被騙嗎？」
  4. 「即時＋暫停的節奏，會不會太快或太慢？」
- 觀察員逐場記錄（對應 H-01）：開局後是否無協助完成第一次移動、生產、掃描；觸控誤觸次數。
- 匿名化後以 Playtest report 模板開 issue；原始紀錄不進 repo。
- **驗收**：第 6 節的 gate 表全部有實測值（或標明 `NOT MEASURED` 與原因），判定結果記錄在本卡。

### CP1-09｜視覺與音效方向（平行，不阻塞 gate）

- 依 `docs/art-direction.md` 第 8 節：以 three.js 原型渲染寫實方向的目標畫面（戰略、作戰、戰術三個尺度，低／高畫質），截圖附 draw calls、三角形數與量測條件。不使用 AI 生圖。
- 目標畫面需呈現四種情報標記與底部按鈕列，敵我以形狀＋顏色雙重區分，無真實國籍標誌或部隊標記。
- 音效清單與動畫清單：情報事件、指令回饋、交戰、介面的聲音描述與參考（不收第三方音檔進 repo）；縮放過渡、擊毀、情報事件的時長與表現。
- **驗收**：目標畫面與原型存於內部（實機重現前不進 repo）；`docs/art-direction.md` 第 3 節預算依原型量測更新；owner 確認方向（最晚 CP2 開工前）；CP2 卡片列出 iPad 實機量測項目與 GPU 記憶體預算。

## 6. 出關條件（CP1 Gate）

技術門檻（全部必須成立）：

- [ ] 技術卡 CP1-01～07 驗收全部打勾，`main` CI 綠燈。CP1-09 為平行的美術探索，**不阻擋出關**；美術方向可在 gate 會議或之後另行選定，最晚在 CP2 開工前。
- [ ] iPad Safari（觸控）與桌機瀏覽器各能從開局打到結算。

試玩門檻（建議值，可於 gate 會議調整，但要記錄理由）：

| 指標 | 通過 | 量法 |
|---|---|---|
| 試玩人數 | ≥ 5 人完成 ≥ 1 局 | 計數 |
| 情報理解 | ≥ 80% 能正確說明已確認／未確認接觸的差別 | 訪談題 1 |
| 情報影響部署 | ≥ 60% 至少一次因情報改變部署 | 訪談題 2 為主，CP1-07 腳本配對結果交叉確認 |
| 欺敵有效 | 有使用假接觸的局中，≥ 50% 至少一次調動 AI | CP1-07 腳本 |
| 操作可及（H-01） | ≥ 80% 無協助完成第一次移動與生產 | 觀察紀錄 |
| 局長 | 真人對局中位數 8–12 分鐘 | CP1-07 腳本 |

判定：

- **通過** → 進 CP2（雙尺度真機切片），H-01／H-03 記為「初步支持」。
- **情報理解或影響部署未達標** → 觸發 ADR-0001 重新評估條件 1：先調可讀性與參數再測一輪；第二輪仍未達標就把 DEC-02 的同步回合對照提前到 CP2。
- **只有局長、欺敵有效或操作可及未達標** → 調參數或 UI，不阻擋 CP2。
