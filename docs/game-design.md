# Twinfront Command — 遊戲設計（Game Design）

- 版本：v0.2｜2026-11-21
- 文件角色：核心循環、候選規則、數值與設計問題的單一來源。產品需求看 [`product-brief.md`](product-brief.md)；技術契約看 [`architecture.md`](architecture.md)。
- 狀態：全部數值都是**灰盒候選值**，未經實測。沒有標【已決】的規則，都可以在 W2 前調整。
- 設計原則：小規模、可讀、可重播、10 分鐘內完成一局。

## 1. 設計支柱

1. **雙線取捨**：玩家要在兩條路線之間分配生產與防守，不能只堆一條路。
2. **下令，不微操**：玩家決定兵種、路線、時機與研究；單位自動執行。
3. **讀得懂**：輪廓、圖標、動態與位置都能辨識敵我與兵種；顏色只是輔助。
4. **一場小戰役**：不是歷史模擬器，也不是基地建設；重點是 8–12 分鐘內的攻防節奏。
5. **可重現**：同種子、同指令、同規則版本得到相同結果；平衡討論才有共同基準。

## 2. 對局結構

| 項目 | 候選設定 | 狀態 |
|---|---|---|
| 模式 | 1v1，玩家對 AI；單機 | 【暫定】P0 |
| 地圖 | 1 張雙路對稱地圖 | 【暫定】P0 |
| 總部 | 每方 1 座；被攻破即終局 | 【已決】 |

| 局長 | 目標 8–12 分鐘；12 分鐘進入判定 | 【暫定】 |
| 資源 | 補給（supply）單一資源 | 【已決】 |

### 2.1 地圖拓撲（暫定）

```
北路：  [A 總部]──[A 北前哨]──────────[B 北前哨]──[B 總部]
南路：  [A 總部]──[A 南前哨]──────────[B 南前哨]──[B 總部]
                  ↑ A 的防線              ↑ B 的防線
```

- 每方在每條路各有一座前哨，位於自己的總部前；全場 4 座。
- 攻擊方必須摧毀敵方在該路的前哨，才能推進到敵方總部。
- 前哨是防禦建築，不是可佔領的中立點；摧毀後該路開放，前哨不會重生。
- MVP 的兩條路不互通；單位在生產時選路，之後不換線。
- 這個拓撲是**暫定**。原企劃的「2 個前哨」沒有說清楚是總數還是每方，這裡採用「每方 2 座」以支撐雙線防守與經濟計算；若試玩顯示防守太被動，再考慮中央通道或前哨可佔領。

### 2.2 路線選擇（暫定）

- 每一筆生產訂單都要選北路或南路；UI 預設沿用上一筆的選擇，一鍵切換。
- 玩家可以自由把生產分散到兩路，沒有全域「主攻路線」鎖定。
- 單位在總部生成，沿選定路線前進；不會自動換線。
- 這是「雙線指揮」的核心操作。若試玩顯示玩家只想單線堆兵，先檢查 UI 與 AI 壓力，再考慮地圖中央通道；不要用自動作弊把單位送到另一路。

## 3. 核心循環

```
開局 → 部署與排產 → 自動交戰 → 擊破前哨 → 獲得補給
     → 研究或補兵 → 推進 → 攻破總部 → 結算 → 再戰
```

每個循環都應該產生一個可理解的取捨：現在補兵，還是先研究？守哪一路，還是冒險推進？打前哨拿補給，還是直接繞過？

## 4. 經濟

| 項目 | 候選值 | 說明 |
|---|---|---|
| 起始補給 | 120 | 足夠開局生產 2–3 個單位或一個研究 |
| 常態收入 | 每 10 秒 +15（1.5／秒） | 不隨時間加速；避免後期暴增 |
| 前哨獎勵 | 每個敵方前哨**首次**摧毀 +60 | 兩座合計 +120；不重複發獎 |
| 普通單位擊破 | 0 | 避免可重複刷資源 |
| 其他設施 | 0 | MVP 不給資源；避免來源過多 |
| 資源上限 | 無硬上限 | 但生產與佇列會自然限制支出 |

### 4.1 補給預算檢查

這是用候選值做的粗算，不是平衡結論；目的是確認「經濟規模」與「效能目標」沒有互相矛盾。

| 項目 | 每方 12 分鐘估算 |
|---|---|
| 起始 | 120 |
| 常態收入（720 秒 × 1.5） | 1,080 |
| 兩座敵方前哨 | +120 |
| **總補給** | **約 1,320** |
| 兩項研究 | -180 |
| 1–2 座砲塔 | -65 ～ -130 |
| 可用於單位的補給 | 約 1,010 ～ 1,140 |
| 以平均單價 57.5 計算 | 約 18–20 個單位 |
| 以步兵為主（單價 30） | 約 33–38 個單位 |

**結論：**

- 預期實戰是**每方約 18–30 個可動單位**，全場約 36–60 個。
- 「全場 60 個可動單位」是正常壓測上限，不是每方 60，也不是每波都這麼多。
- 若試玩顯示每方經常達到 60，代表經濟或單位上限需要調整；不要默默把效能預算提高到 120 當成常態。
- 前哨獎勵合計約占總補給 9%，單看補給不是壓倒性優勢；真正的雪球風險來自「路線打開後的推進壓力」。平衡實驗要分開測獎勵與路線效果。

### 4.2 平衡實驗

若「先破前哨幾乎必勝」：

1. 先分離兩個效果：(a) +60 補給、(b) 該路開放帶來的推進壓力。
2. 若只有 (a) 造成雪球，降低獎勵或提高常態收入。
3. 若主要是 (b)，調整前哨耐久、防守位置、AI 回防或地圖，而不是加第二種貨幣。
4. 不要用「降低全部收入」同時解決兩個問題；那會讓局長變長、單調。

## 5. 生產與單位

### 5.1 生產規則

| 規則 | 候選值 | 狀態 |
|---|---|---|
| 生產佇列 | 每方 1 條，最多 3 筆待生產訂單 | 【暫定】 |
| 佇列上限的意義 | 只計算**排隊中**的訂單，不含場上存活單位 | 【已決】文件修正 |
| 每方單位上限 | 場上＋佇列合計 30；全場 60 | 【暫定】P0 |
| 下單扣費 | 下單立即扣補給 | 【暫定】 |
| 滿額行為 | 場上＋佇列合計達 30 時拒絕下單並提示，不自動退款 | 【暫定】 |
| 生產時間 | 見單位表；受工業效率影響 | 【暫定】 |
| 生產與研究 | 可同時進行；一次只研究一項 | 【暫定】 |

> 文件修正：v0.1 寫「上限含排隊與存活單位」，若照字面解讀，每方最多只有 3 個單位，與 4 種兵、60 單位壓測、雙線推進全部矛盾。v0.2 明確拆成「佇列上限 3 筆」與「場上＋佇列合計上限 30」。

### 5.2 單位表

| 單位 | 造價 | 生產時間 | 主要角色 | 傷害標籤 | 備註 |
|---|---|---|---|---|---|
| 步兵 | 30 | 5 秒 | 便宜、佔位、早期壓力 | 反步兵 | 以數量與路線佔領為主 |
| 坦克 | 70 | 10 秒 | 推進、吸收傷害 | 反裝甲、反設施 | 裝甲強化 +15% 生命（候選） |
| 火砲 | 85 | 12 秒 | 拆設施、遠程壓制 | 反設施 | 移動慢、需要保護 |
| 偵察車 | 45 | 6 秒 | 壓制火砲、騷擾 | 反火砲 | 脆、速度快 |

- 單位的 HP、傷害、射程、速度尚未定案；第一輪灰盒用可調參數，不寫死在文件。
- 相剋以抽象傷害標籤表達，不做複雜物理或裝甲角度。
- 每個單位都要有可辨識的輪廓與圖標；不能只靠顏色區分敵我。
- 海空單位、碉堡不在 P0；內容 schema 仍預留 `domain: ground | air | sea`。

### 5.3 固定砲塔

- 造價 65；只能放在指定建築格。
- 角色：固定防守、拖延推進、保護前哨與總部。
- 不佔用生產佇列；建造時間與升級待定。
- 碉堡若納入，必須與砲塔有不同角色（例如駐軍、阻擋、反步兵），否則不要為了題材硬加。

## 6. 研究

| 研究 | 造價 | 時間 | 候選效果 | 備註 |
|---|---|---|---|---|
| 裝甲強化 | 90 | 20 秒 | 坦克生命 +15% | 只影響坦克；實際套用方式待內容 schema |
| 工業效率 | 90 | 20 秒 | 生產時間 -15% | 影響所有單位；不影響研究時間 |

- 兩條研究線各 1 級；MVP 不做多級科技樹。
- 研究與生產可同時進行；一次只能研究一項。
- 研究完成時間要進統計與時間軸，方便回顧「先兵還是先科技」的取捨。
- 研究效果是乘算或加法、是否疊加，必須在內容資料與 ADR 中固定，不能只寫在 UI 文案。

## 7. 人工智慧（AI）

| 項目 | 候選設計 | 狀態 |
|---|---|---|
| 經濟 | 使用與玩家相同的收入、成本與生產時間；不得資源作弊 | 【已決】 |
| 決策頻率 | 每 2 秒檢查威脅與預算 | 【暫定】 |
| 路線分配 | 依玩家兵力分布、前哨狀態與自身 composition 決定主攻／防守路 | 【暫定】 |
| 兵種組成 | 至少會針對玩家 composition 調整；不能只會單一兵種 | 【暫定】 |
| 難度 | MVP 至少 2 級：標準、低壓；低壓只調整反應延遲與進攻閾值，不調資源 | 【暫定】 |
| 重播 | AI 產生的指令要記錄進 replay；AI 版本或種子也要記錄 | 【已決】技術契約 |
| 驗收 | 不作弊、能主動求勝、局長分布接近目標、玩家能說出 AI 的一次應對 | 【暫定】 |

- AI 的「每 2 秒檢查」不是硬性 tick；實際決策可以在檢查點產生指令，於下一個 tick 生效。
- 低壓模式是難度與無障礙選項，不是隱藏作弊；UI 要說明它改變什麼。
- 若 AI 只會被動防守，12 分鐘會變成拖時間；驗收要看 AI 主動進攻的頻率與局長分布。

## 8. 終局與結算

### 8.1 終局

1. 任一方總部生命歸零 → 該方落敗；若同一個 tick 雙方總部都歸零 → 平局。
2. 12 分鐘未破 → 比較總部剩餘生命百分比；高者勝。
3. 仍相同 → 比較已摧毀的敵方前哨數；多者勝。
4. 仍相同 → 平局。
5. 終局後拒絕任何戰局指令；只接受再戰、返回選單、查看統計。

- 「12 分鐘平局」是否令人滿意，待 DQ-06。若試玩顯示被動拖時間太多，考慮延長賽或突然死亡，但不要讓局長失控。
- 判定由事件推導，不靠 UI 自己算；擊毀事件以 `entityId` 去重。

### 8.2 結算畫面

MVP 顯示：

- 勝負與結束原因（總部被攻破、時間到、平局）。
- 雙方擊毀數：按陣營與單位類型；只顯示已實裝類型，不顯示海空空計數。
- 雙方損失、建造數、補給來源與支出摘要。
- 研究完成時間。
- 簡短時間軸：前哨、總部、關鍵研究。
- 再戰、返回選單。

P1 才考慮「勝因」自動標籤、分享卡、完整回放 UI。MVP 的回放主要用於測試與除錯，不是玩家功能。

## 9. 教學

MVP 用「做中學」的三步驟，不用長篇彈窗：

1. **部署**：引導玩家下第一筆步兵訂單，選一條路，看到單位自動前進。
2. **取捨**：引導玩家擊破第一個前哨，說明補給獎勵，然後提示補兵或研究二選一。
3. **目標**：標示敵方總部與勝利條件，讓玩家完成一局；允許跳過。

驗收：新玩家在無口頭協助下完成首局；至少能說出一次「為什麼我選補兵或研究」。若做不到，先修教學與 UI，不要加更多文字。

## 10. 可讀性與無障礙

- 敵我識別：形狀、輪廓、圖標、位置與動態都要能區分；顏色不是唯一通道。
- 觸控目標：主要按鈕至少 44×44 px；避免 hover-only 操作。
- 暫停：任何時候可暫停；暫停時不推進遊戲時間。
- 減少動態：可關閉螢幕震動、粒子與快速閃爍；不做閃光敏感風險效果。
- 字級與對比：UI 可縮放；重要數字（補給、佇列、總部生命）在任何畫質下可讀。
- 音訊：MVP 暫定無音訊；若加入，提供音量與靜音，重要音效要有視覺替代。
- 低壓模式：降低 AI 反應與進攻頻率，不改變規則與數值。

## 13. 變更規則

- 這份文件的數值都是候選值；變更不需要開 ADR，但要在 PR 說明「改了什麼、為什麼、預期影響」。
- 若變更會影響 P0 範圍、對外承諾、效能預算或經濟規模，開 DEC 或在既有 DEC 下補證據。
- 平衡變更要附：變更前後、測試種子、預期影響、實際觀察；不要只貼新數字。
- 內容 JSON 上線後，數值以 JSON 為準；本文件只保留摘要與連結，避免第二份基準。
