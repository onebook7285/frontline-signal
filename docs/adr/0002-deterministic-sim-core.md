# ADR-0002：決定性模擬核心

- 狀態：Accepted（暫定）
- 日期：2026-11-21
- 決策者：維護者／工程
- 相關：DR-06、DEC-02、TQ-02、TQ-04、TQ-07

## 背景

- 這是一款即時／回合都可能成立的策略遊戲；平衡與 bug 討論需要可重現的基準。
- 單位、傷害、資源、AI 指令與勝負判定會互相影響；靠手動重現很難除錯。
- 目標平台包含瀏覽器與 iPad；不同裝置的浮點、時間與事件順序可能不同。
- 未來若做 Roblox 切片，規則與測試向量要能對照。

## 決策

建立一個**純 TypeScript、與渲染／時間無關**的模擬核心：

- 固定 10 Hz tick；時間只以 tick 編號表示。
- 種子 RNG；RNG 呼叫順序是規則的一部分。
- 位置、生命、傷害、計時使用整數或整數定點；避免平台相關的浮點數學。
- 指令依 `(tick, side, seq)` 排序；每個 tick 先驗證指令，再結算。
- 產生 `Event`、`Snapshot` 與 `Replay`；replay 包含 AI 指令。
- `packages/sim` 不依賴 DOM、牆鐘、瀏覽器 API 或網路。
- 前端只讀快照與事件，不直接修改模擬狀態。

## 後果

**正面：**

- 同種子、同指令可重現；bug 與平衡爭議有共同基準。
- 可在 Node 與瀏覽器跑同一套 fixtures；CI 可以抓回歸。
- 節奏（即時／回合）可以留在 app 層，不必重寫模擬。
- 未來移植時，規則與測試向量可作為參考。

**負面／成本：**

- 整數定點與確定性排序增加實作複雜度。
- 不能用方便的引擎物理、`Math.random` 或時間函式。
- 每次改變 tick 順序、RNG 或傷害結算都要昇 `rulesVersion` 並補 fixtures。
- AI 若在模擬外即時生成指令，replay 必須記錄指令，不能只記種子。

**影響：**

- 需要穩定的序列化與 `finalHash`。
- 需要一套 fixture 管理與版本規則。
- 前端需要插值與快照緩衝，不能直接讀可變狀態。

## 替代方案

| 方案 | 為什麼不選 |
|---|---|
| 引擎內建物理與隨機 | 難以跨平台重現；除錯成本高 |
| 浮點模擬＋容忍誤差 | 平衡與 replay 比較會變得模糊 |
| 只錄玩家指令、重跑 AI | AI 改版後舊 replay 會失效；難以除錯 |
| 先不做 replay，之後再補 | 規則與 bug 會累積到無法回溯 |

## 證據

- 目前是設計決策，尚未有本專案的 replay 實作。
- M0 的 smoke fixture 會驗證：同種子同指令 → 同事件與 `finalHash`。

## 重評條件

- 整數定點造成開發速度或可讀性嚴重下降，且找不到替代的確定性方案。
- 效能無法在 10 Hz／60 單位下達標，且最佳化無效。
- 遊戲型態改變（例如改成即時物理為主），使固定 tick 不再合適。
