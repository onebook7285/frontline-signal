# Twinfront Command — 試玩驗證（Playtesting）

- 版本：v0.2｜2026-11-21
- 文件角色：試玩協議、樣本、指標與判斷規則的單一來源。
- 目的：驗證「雙路、短局、下令後自動交戰」是否真的產生有趣決策；不是證明遊戲好玩，也不是統計研究。
- 適用：W2 節奏 A/B、W6 MVP 驗收、M3 封測。每輪的 build、規則版本與樣本都要記錄。

## 1. 我們要回答的問題

| 問題 | 對應決策 | 需要的證據 |
|---|---|---|
| 玩家能不能在無口頭協助下完成首局？ | DEC-02、DR-01、DR-02 | 完成率、卡住的位置、首次正確操作時間 |
| 即時可暫停與同步回合，哪個在觸控上更清楚？ | DEC-02 | 交叉試玩、誤觸、理解、局長、偏好 |
| 玩家能不能說出一次「補兵 vs 研究」的取捨？ | DEC-02、H-03 | 訪談回答、實際選擇、事後回顧 |
| 先破前哨是否造成雪球？ | H-03、R-03 | 首座前哨時間、補給差、勝負、逆轉案例 |
| 地圖與前哨規則是否讀得懂？ | DQ-01、DQ-02 | 玩家是否能畫出/說明路線與目標 |
| 教學與結算是否足夠？ | M2 | 完成率、再玩意願、結算理解 |

## 2. 樣本

- 每輪 **5–8 人**；不要只找熟人，也不要只找 RTS 老手。
- 建議組成：
  - 至少 2 人以觸控／平板為主要裝置。
  - 至少 2 人玩過 RTS 或塔防。
  - 至少 2 人很少玩即時策略。
  - 盡量包含 1 位不熟悉本專案的人。
- 同一輪內用**交叉設計**：一半先玩即時、一半先玩回合；第二場換另一種。順序要記錄。
- 這是便利樣本，不是統計推論；結果只用來做方向判斷，不能說「玩家都喜歡」。
- 招募從 W2 前開始；不要等到 W6 才找人。準備 3–5 名備取。

## 3. 倫理與資料

- 事前說明：目的、時長、會記錄什麼、可以隨時停止、不是考試。
- 參與者用代碼（P01、P02…）記錄；姓名、聯絡方式、公司、職稱不進 public repo。
- 錄影、錄音、截圖要另外取得同意；不同意就只做文字筆記。
- 公開版本只放匿名聚合與觀察，不放可識別個資、逐字稿或未同意的引述。
- 原始筆記與同意紀錄放私人區；保存期限與刪除方式由維護者決定。
- 不要讓參與者覺得「玩不好是他們的問題」；先修 UI 與教學，再怪玩家。

## 4. 每場流程（60–75 分鐘）

| 階段 | 時間 | 做什麼 | 不要做什麼 |
|---|---|---|---|
| 開場 | 5 分 | 說明目的、同意、裝置、錄影；確認是否玩過類似遊戲 | 不要先教操作或解釋規則 |
| 第一場 | 15–20 分 | 玩家自行開始；主持人只說「請邊玩邊說你在想什麼」 | 不要指路、不要說「你應該…」 |
| 中場訪談 | 10 分 | 問：你剛才想做什麼？卡在哪？怎麼判斷勝負？ | 不要先給正確答案 |
| 第二場（另一節奏） | 15–20 分 | 同地圖、同種子或同難度；更換節奏 | 不要讓兩場的教學／提示不同 |
| 事後訪談 | 10 分 | 取捨、偏好、誤觸、可讀性、再玩意願 | 不要用誘導式問題 |
| 收尾 | 5 分 | 感謝、說明資料用途、詢問是否願意再測 | 不要承諾一定會改 |

### 4.1 主持人腳本要點

- 開場只說：「這是一個早期原型，沒有正式美術；我想知道你能不能自己玩懂，不是測試你。」
- 卡住時先等 20–30 秒，再問「你現在在想什麼？」不要直接給答案。
- 玩家問「這個按鈕是什麼？」可以回答介面事實，但不要給策略建議。
- 記錄「第一次成功部署」「第一次正確研究」「第一次理解勝負條件」的時間點。
- 結束後問一個強迫選擇：「如果只能保留一種節奏，你選哪個？為什麼？」偏好不是唯一依據，但要記錄。

## 5. 指標

| 指標 | 怎麼記 | 用途 |
|---|---|---|
| 完成率 | 是否在無口頭協助下走到結算 | 硬門檻 |
| 首次部署時間 | 開局到第一筆有效生產訂單 | 教學與 UI |
| 首次正確研究時間 | 開局到第一個研究完成，且玩家能說明理由 | 理解 |
| 誤觸次數 | 非預期選路、誤下單、誤點建築 | 觸控 |
| 無效操作 | 資源不足、終局後下單、重複點擊 | UI 回饋 |
| 閒置時間 | 超過 10 秒沒有有效操作的時間占比 | 節奏 |
| 補給支出 | 生產／研究／砲塔占比 | 取捨 |
| 首座前哨時間 | 第一座前哨被摧毀的時間與歸屬 | 雪球 |
| 局長 | 開局到結算的時間 | 8–12 分鐘目標 |
| 勝負理解 | 玩家能否說出為什麼贏／輸 | 可讀性 |
| 取捨理解 | 能否說出一次補兵 vs 研究的原因 | 核心樂趣 |
| 偏好 | 兩種節奏的強迫選擇 | DEC-02 輔助 |
| 挫折／無聊 | 1–5 分，加上原因 | 體驗 |
| 再玩意願 | 1–5 分 | M2 訊號 |

## 6. 判斷門檻

### 6.1 硬門檻

- **完成率 ≥80%**：至少 4/5 或 5/8 的參與者在無口頭協助下完成首局。
- **無致命觸控錯誤**：沒有人因為 UI 而無法完成必要操作；誤觸可以修正，但不能卡死。
- **局長中位數 8–12 分鐘**：若偏離，先調經濟與 AI，不要直接改目標。
- **取捨理解 ≥70%**：至少 7/10 的參與者能說出一次補兵／研究的理由。

### 6.2 DEC-02 的決策規則

W2 用同地圖、同種子、同難度比較「即時可暫停」與「同步回合」：

1. 若即時通過硬門檻、回合未通過 → 選即時。
2. 若回合通過、即時未通過 → 選回合。
3. 若兩者都通過 → 預設選即時（較接近原始構想），除非即時在觸控或理解上顯著較差。
   - 「顯著較差」的操作定義：至少 2 位參與者無法完成關鍵操作，或即時的平均誤觸次數是回合的 2 倍以上。
4. 若兩者都未通過 → 不要二選一；先修 UI、教學與經濟，再測一輪。
5. 若結果因裝置而異 → 以 iPad／觸控為優先，因為產品承諾包含觸控；桌面表現只作輔助。
6. 偏好投票只作輔助，不能覆蓋硬門檻與實際操作觀察。

### 6.3 雪球判斷

- 記錄首座前哨被摧毀的時間、摧毀方、當時補給差、之後 2 分鐘的推進與勝負。
- 若「先破前哨」與勝利高度相關，先分離：(a) +60 補給、(b) 該路開放。不要直接加第二種貨幣。
- 若多數局在首座前哨後 2 分鐘內勝負已定，考慮調前哨耐久、防守位置、AI 回防或地圖；不要只調獎勵。
- 逆轉案例要記錄：什麼情況下落後方贏了？這比平均數更有用。

## 7. 每輪要記錄的建置資訊

- Git commit SHA 與 `rulesVersion`、`schemaVersion`。
- 使用的種子、地圖、AI 難度、模式（即時／回合）。
- 裝置型號、OS、瀏覽器版本、視窗大小、畫質。
- 是否有錄影／錄音同意。
- 主持人與參與者代碼。

## 8. 結果怎麼寫

- 原始筆記（含可識別資訊）放私人區。
- 公開摘要只寫：日期、build、樣本數與組成、聚合指標、主要觀察、反例、限制、下一步。
- 不要寫「玩家覺得很好玩」這種沒有證據的結論；寫「5/6 完成首局，3/6 能說出補兵理由」。
- 不要隱藏失敗案例；失敗案例是下一輪設計的輸入。
- 每輪結束後更新 `game-design.md` 的 DQ 狀態與 `roadmap.md` 的風險；必要時開 DEC。
