# 協作方式（Ways of Working）

- 版本：v0.2｜2026-11-21
- 文件角色：Issue、PR、ADR、決策、文件與公私分界的流程單一來源。
- 適用：維護者、貢獻者、AI 輔助開發者、試玩主持人。
- 原則：小步、可驗證、單一來源、公開前先假設全世界都看得到。

## 1. 角色

| 角色 | 責任 | 不是什麼 |
|---|---|---|
| 維護者（Maintainer） | 最終產品決策、合併 PR、發布、處理安全與行為問題 | 不是唯一寫程式的人 |
| 貢獻者（Contributor） | 提 issue、送 PR、寫文件、做美術或試玩 | 不需要先取得許可才能開 issue |
| 設計審閱者 | 對規則、可讀性、節奏提供意見 | 不是橡皮圖章 |
| 試玩主持人 | 招募、主持、記錄、匿名化 | 不負責替玩家操作 |
| AI 輔助者 | 在人類指示下實作、研究、審閱 | 不能自行發布、不能繞過人類審查 |

小團隊常見一人多角色；文件用角色而不是人名，避免換人後全部失效。

## 2. 公開／私人分界

這個 repo 是 public。**公開是永久的**：就算之後刪除，快取、fork、搜尋引擎都可能留著。不確定時，先不要放。

| 內容 | 公開 repo | 私人區 |
|---|---|---|
| 產品需求、設計、架構、路線圖 | ✅ | 可放更完整的理由與內部限制 |
| ADR、公開研究、試玩協議 | ✅ | 原始筆記、個資、未匿名引述 |
| Issue、PR、測試證據 | ✅（去識別化） | 涉及帳號、主機、私人 repo 的細節 |
| 實際工時、個人排程、容量 | ❌ | ✅ |
| 內部 CI／主機規格、runner 編號、內網入口 | ❌ | ✅ |
| 私人 repo 的程式、授權盤點、耦合分析 | ❌ | ✅ |
| Agent 分工、模型選擇、worktree 安排 | ❌ | ✅ |
| 預算、帳號狀態、年齡驗證、法律／商標諮詢 | ❌ | ✅ |
| 試玩者姓名、聯絡方式、逐字稿 | ❌ | ✅ |
| 未公開的合作對象、平台往來 | ❌ | ✅ |

**去識別化規則：**

- 主機名、內網 IP、runner 編號、私有 repo URL 一律不出現。
- 裝置可以寫「低階 Windows 內顯筆電（型號待定）」，不要寫資產編號或序號。
- 試玩者只寫 P01、P02 與匿名背景（例如「平板為主、少玩 RTS」）。
- 截圖要檢查瀏覽器分頁、書籤、通知、帳號名稱。
- PR 前用 `git diff --cached` 自己看一遍；不要只靠 `.gitignore`。

## 3. 決策與編號

| 前綴 | 用途 | 放哪裡 |
|---|---|---|
| `REQ-xx` | 原始需求 | `product-brief.md` |
| `H-xx` | 設計假設 | `product-brief.md` |
| `DR-xx` | 衍生需求／設計限制 | `product-brief.md` |
| `DEC-xx` | 產品或專案決策 | `product-brief.md`；私人台帳可補內部理由 |
| `DQ-xx` | 設計問題 | `game-design.md` |
| `TQ-xx` | 技術問題 | `architecture.md` |
| `ADR-xxxx` | 耐久技術決策 | `docs/adr/` |
| `R-xx` | 風險 | `roadmap.md` |
| `CHG-xxx` | 計劃基線變更 | 私人台帳；公開文件只留結果 |

**規則：**

- 編號一旦使用就不重用；被取代的決策保留舊紀錄，標記 `Superseded by ...`。
- 公開文件只放對貢獻者有用的理由；內部成本、帳號、主機、私人 repo 的理由留私人區。
- 同一件事不要同時在 DEC 與 ADR 寫兩份完整理由：DEC 管產品／範圍，ADR 管技術；互相連結即可。
- 決策要有日期、狀態、負責角色、重評條件。沒有重評條件的「已決」通常只是暫時偏好。

### 3.1 什麼時候要開 DEC／ADR

- **開 DEC**：改變產品範圍、目標玩家、對外承諾、里程碑、平台方向、授權或商業意圖。
- **開 ADR**：改變模擬契約、渲染器、資料格式、部署模型、依賴策略、測試策略，或任何難以回頭的技術選擇。
- **不開**：數值微調、文案、區域重構、測試補強。這些用 PR 說明即可。
- **判斷原則**：如果三個月後有人會問「為什麼當初這樣選？」，就寫下來。

### 3.2 決策流程

1. 開 issue 或寫一頁提案：問題、選項、證據、建議、影響。
2. 在 issue 討論；需要時做小原型或量測。
3. 維護者拍板；把結果寫進 DEC 或 ADR。
4. 建立實作 issue，連回決策。
5. 實作完成後，在決策文件補「實際結果」與「重評日期」。

不要用聊天室結論當唯一紀錄；聊天可以討論，決策要落在文件。

## 4. Issue

### 4.1 每張 issue 要有什麼

- 問題或目的（為什麼要做）。
- 範圍與**不在範圍**。
- 驗收條件（可觀察、可測試）。
- 依賴與被依賴。
- 影響區域（sim／web／content／art／qa／platform／docs）。
- 里程碑與大小（S／M／L）。
- 若需要決策，標 `needs:decision` 並連到 DEC／ADR。

### 4.2 標籤

| 標籤 | 用途 |
|---|---|
| `type:bug` | 行為與預期不符 |
| `type:feature` | 新功能或規則 |
| `type:task` | 工程、文件、流程工作 |
| `type:research` | 有日期的研究，不一定會實作 |
| `area:sim` / `area:web` / `area:content` / `area:art` / `area:qa` / `area:platform` / `area:docs` | 影響區域 |
| `status:blocked` | 等決策、依賴或外部資訊 |
| `needs:decision` | 需要 DEC／ADR |
| `good first issue` | 不需背景知識，適合新貢獻者 |
| `size:S` / `size:M` / `size:L` | 相對大小，不是工時承諾 |

### 4.3 Definition of Ready

- 問題清楚，能寫出一句「做完之後什麼會不一樣」。
- 驗收條件可觀察；不是「做得好看」。
- 沒有未解的阻塞決策；若有，先開 DEC／ADR。
- 影響區域與依賴已標。
- 大小不超過 M；太大就拆。

### 4.4 Definition of Done

- 程式／文件完成，符合範圍。
- 測試或證據到位；規則變更有 replay fixture。
- 文件與索引更新；必要時補 ADR／DEC。
- 沒有 secrets、內網資訊、個資、未授權素材。
- 可讀性與無障礙沒有退步（UI 變更）。
- PR 說明包含測試結果、風險、未測事項。
- Issue 連回 PR，PR 合併後 issue 關閉。

## 5. Pull Request

### 5.1 原則

- 一個 PR 一件事；避免「順便重構」。
- 先開 issue 再開 PR；例外是錯字、連結、明顯的 docs 修正。
- PR 標題用 `feat:`、`fix:`、`docs:`、`test:`、`chore:`、`refactor:` 前綴。
- 分支名稱：`feat/<topic>`、`fix/<topic>`、`docs/<topic>`、`chore/<topic>`；AI 協作可用 `agent/<tool>/<topic>`，但不要放個人或內部代號。
- 預設 squash merge；PR 標題會成為 main 的 commit 訊息。

### 5.2 PR 必填

- 摘要與動機。
- 連結的 issue。
- 變更類型與影響區域。
- 測試證據（指令、結果、截圖／錄影）。
- 風險與未測事項。
- 文件／ADR 是否更新。
- 素材來源與授權（若涉美術、音訊、字型）。
- 是否含 AI 輔助；若大部分由 AI 產生，請註明，方便審閱。

### 5.3 規則變更的 PR

- 附上變更前後、種子、預期影響。
- 更新或新增 fixture；CI 要能重播。
- 若改變 tick 順序、RNG 使用或傷害結算，昇 `rulesVersion` 並在 PR 說明。
- 不要只貼新數值；要說明為什麼改、預期解決什麼問題。

### 5.4 審閱與合併

- 公開貢獻者的 PR 由維護者審閱；作者不自行合併。
- 維護者自己的 PR 仍要通過 CI；若需要第三人審閱，在 issue 註明。
- 合併前確認：CI 綠、沒有 secrets、文件同步、驗收條件滿足。
- 有意見分歧時，回到 issue 寫選項與證據；不要在 PR 留言串來回消耗。

## 6. 文件

- 先看 [`docs/README.md`](README.md) 的單一來源規則。
- 新文件先問「它是不是某類資訊的唯一來源」；不是的話，不要新增。
- 日期用 ISO `YYYY-MM-DD`；版本用 `v0.x`；狀態用【已決】【暫定】【假設】【待決】【不做】。
- 相對連結優先；對外連結要確認可讀，不連私人 repo、內網或追蹤參數。
- 文件以繁體中文為準；英文摘要、翻譯、名詞校正歡迎。
- HTML、簡報、PDF 若存在，標明「快照」與產生日期；不要手改快照。
- 每次里程碑更新 `docs/README.md` 的基線與下次檢視日期。

## 7. 版本與發布

- 程式尚未開始前，只有文件基線（v0.2）；不假裝有 release。
- 程式開始後：
  - app 版本用 semver；`0.x` 期間不保證相容。
  - `schemaVersion` 管內容資料形狀；`rulesVersion` 管規則行為。
  - 破壞性變更要補 migration，或明訂不支援舊版。
  - Replay 只保證在同一 `rulesVersion` 內重現；跨版本要警告。
- Release notes 從合併的 PR 與里程碑整理；不另外維護工作日誌。
- 每個 release 要能回滾到上一個靜態版本；預覽與正式使用不可變版本。

## 8. AI 輔助貢獻

- 歡迎使用 AI 輔助；貢獻者仍對正確性、授權、測試與安全負責。
- AI 產生的變更要說明範圍；不要讓它自動合併、發布或改 repo 設定。
- 大型重構、依賴新增、schema 變更要先開 issue，不要讓 AI 自行決定。
- AI 不得讀取或貼出私人區內容到 public repo；不得把 token、主機名、私有 repo 寫進程式或文件。
- 人類審閱要特別看：幻覺 API、未測路徑、抄來的程式碼授權、過度重構、遺漏的錯誤處理。

## 9. 安全與隱私

- 發現安全問題：用 GitHub Security Advisories 私下回報，不要開 public issue。
- 不在 repo 放 token、密碼、`.env`、私鑰、內網 URL、私有 repo 連結。
- 不收集玩家個資；MVP 沒有帳號、後端或分析。
- 試玩資料依 [`playtesting.md`](playtesting.md) 匿名化；原始資料放私人區。
- 內容爭議依 [`content-policy.md`](content-policy.md) 處理；維護者可移除違規內容。

## 10. 社群

- 所有互動遵守 [`CODE_OF_CONDUCT.md`](../CODE_OF_CONDUCT.md)。
- 遊戲內容遵守 [`content-policy.md`](content-policy.md)：虛構陣營、無仇恨符號、無血腥。
- Issue 與 PR 可用中文或英文；維護者盡量以相同語言回覆。
- 不歡迎：騷擾、歧視、仇恨符號、真實政治宣傳、盜版素材、未經同意的個資。
- 貢獻者不需要簽 CLA；送出的程式與文件以 MIT 授權，素材依 `ASSETS.md` 的授權規則。

## 11. 節奏

- 每週一次 issue triage；每個里程碑一次 review。
- 同時只維持 1–2 個進行中的工作流；完成比開始重要。
- 不做每日 standup、不寫流水帳；Issue、PR、ADR 就是紀錄。
- 決策點前先寫一頁簡報；不要用「感覺差不多了」當結論。
