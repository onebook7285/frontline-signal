# Twinfront Command — 路線圖（Roadmap）

- 版本：v0.2｜2026-11-21
- 文件角色：里程碑、工作流、決策點、風險與 cut line 的單一來源。
- 讀者：團隊成員、貢獻者、想了解專案進度的人。
- 前提：小型團隊、part-time、AI 輔助開發；不要把代理並行當成多人全時工期。
- 範圍細節：P0 的完整清單在 [`game-design.md`](game-design.md)；本文件只保留里程碑與驗收。

## 1. 一頁摘要

| 項目 | 目前設定 |
|---|---|
| 目標 | 8–12 分鐘的雙路 1v1 對 AI 策略遊戲 |
| 平台 | Web 優先；桌機與 iPad Safari |
| 目前階段 | M0：規則、架構、灰盒、基準與試玩準備 |
| 下一個決策點 | W2 末：節奏、最低設備、MVP 範圍 |
| 最大風險 | 範圍對 part-time 人力偏大；觸控節奏與雪球尚未驗證 |
| 現在就能做 | 真機基準、灰盒、schema、replay fixture、招募試玩者 |

## 2. 里程碑

| 里程碑 | 時段 | 目標成果 | 出關條件 | 停損／cut |
|---|---|---|---|---|
| **M0 Foundations** | W1–2 | 可比較的灰盒、規則與效能基準、試玩計畫 | 同種子 replay fixture 通過；兩種節奏的灰盒可切換；5–8 名試玩者已排定；三類裝置基准有紀錄 | 做不出有效試玩 → 先砍內容，不延後決策 |
| **M1 Vertical slice** | W3–4 | 從開局到結算的單局可玩 | 在 iPad 上全程觸控完成一局；雙路、經濟、3 種兵、砲塔、前哨、AI v1、結算；replay 通過 | W4 末仍無法端到端 → 啟動 cut line |
| **M2 MVP** | W5–6 | P0 功能與可驗收的品質 | 4 種兵、2 條研究、教學、結算統計、效能門檻、預覽與回滾；至少 5 人完成教學與對局 | 效能未達 → 降視覺負載或降單位上限，不改模擬規則 |
| **M3 Playtest / Beta** | W7–12 | 可讀性、平衡、觸控與穩定度 | 兩輪各 5–8 人；主要可讀性與雪球問題有處理；版本可回滾；第二地圖決策有證據 | 未過不加海空；不為了內容量犧牲可讀性 |
| **M4 Platform decision** | MVP 後 | Web 海空試驗或 Roblox 切片二選一 | 成本、受眾、內容審核、維護責任都有結論 | 成本不符 → 保留 Web 版，不做第二客戶端 |

### 2.1 每週節奏

- **每週一次 triage**：整理新 issue、更新里程碑、移除不再需要的項目。
- **每個里程碑一次 review**：對照出關條件，決定繼續、縮範圍或停損。
- **每個決策點寫一頁決策簡報**：選項、證據、建議、影響；不要只用聊天結論。
- 不做每日工作日志；Issue 與 PR 就是執行紀錄。

## 3. 工作流

| 工作流 | 負責角色 | 目前焦點 | 主要產出 |
|---|---|---|---|
| 產品與設計（PD） | 產品／設計 | 玩家輪廓、節奏 A/B、規則與教學 | DEC、DQ、game-design、試玩結論 |
| 模擬（SIM） | 工程 | tick、經濟、生產、研究、傷害、終局 | `packages/sim`、replay fixtures |
| Web／UI（WEB） | 工程 | 灰盒、觸控、暫停、結算、可讀性 | `apps/web`、瀏覽器 smoke |
| 內容與美術（ART） | 設計／美術 | 視覺支柱、placeholder、素材清單 | `art-direction.md`、`ASSETS.md`、素材 |
| QA／效能（QA） | QA／工程 | 三種場景、真機、存檔恢復 | 測試腳本、量測報告、issue |
| 平台研究（PLAT） | 產品／平台 | Roblox 成本與內容審核 | 有日期的研究筆記、go/no-go |
| 文件與社群（DOC） | 維護者 | 文件單一來源、貢獻流程、英文摘要 | docs、issue templates、release notes |

- 同一時間只讓 1–2 個工作流處於「進行中」；其他排隊。小團隊的瓶頸是切換成本，不是 issue 數量。
- 需要跨工作流的變更（例如新兵種同時改 sim、content、UI、平衡）要開一個整合 issue，不要四張各自為政的票。
- 每張 issue 寫明：目的、範圍、不在範圍、驗收、依賴、可改路徑、測試證據。細節見 [`ways-of-working.md`](ways-of-working.md)。

## 4. 決策點

| 時點 | 決策 | 需要的證據 | 相關文件 |
|---|---|---|---|
| W2 末 | 節奏：即時可暫停或同步回合；碉堡是否進 MVP | 5–8 人交叉試玩；完成率、理解、誤觸、局長 | DEC-02、DQ-01～04、ADR-0004 |
| W2 末 | 最低設備、瀏覽器與效能門檻 | M1 iPad、M1 Pro、低階 Windows 內顯分開量測 | DEC-03、architecture §8 |
| W2 末 | 凍結 P0 與 cut line | P0 驗收條件、容量估算、W4 檢查點 | DEC-06、game-design §11 |
| W4 末 | 垂直切片是否成立 | 端到端一局、觸控、replay | M1 出關條件 |
| W6 末 | 是否進第二張地圖／海空 | 首局理解、重玩意願、效能、實際工時 | M2 出關、DQ-06 |
| M4 | Roblox 是否立案 | 受眾、成本、內容審核、維護責任 | DEC-04、research/roblox-publishing |

## 5. P0 驗收條件

| 類別 | 驗收 |
|---|---|
| 完整對局 | 開局 → 部署 → 交戰 → 前哨 → 研究 → 總部 → 結算 → 再戰，不需重載 |
| 觸控 | 在 iPad Safari 全程完成一局；不需要 hover、右鍵或鍵盤 |
| 決定性 | 同種子、同指令、同 `rulesVersion` → 同事件、同 `finalHash` |
| 重播 | replay fixture 可在 CI 重現；AI 指令有記錄 |
| 經濟 | 資源不為負；佇列與場上上限正確；前哨獎勵只發一次 |
| 終局 | 總部歸零、同 tick 平局、12 分鐘判定與排序正確；終局後拒收指令 |
| AI | 不作弊、能主動求勝、至少有一次可被玩家觀察到的應對 |
| 教學 | 新玩家無口頭協助完成首局；至少能說出一次補兵／研究取捨 |
| 結算 | 擊毀數按類型正確、去重、可再戰；不顯示未實裝類別的空計數 |
| 效能 | 全場 60 單位、M1 iPad p95 幀間隔 ≤33.3 ms；模擬 tick p95 ≤8 ms |
| 穩定 | 連玩 3 局、切背景／恢復、存檔損壞，皆不重載、不卡死 |
| 載入 | 首局必要下載 ≤5 MiB（壓縮後）；實際以量測為準 |

## 6. Cut line

如果 W4 末仍無法端到端完成一局，按以下順序砍，**不要砍可讀性與決定性**：

1. 第 4 種兵（偵察車）→ P1。
2. 第 2 條研究線（工業效率）→ P1。
3. 「勝因」自動標籤、分享卡、完整回放 UI → P1。
4. 教學 polish → 先用一頁圖文說明；做中學教學留到 M3。
5. 第二張地圖、海空、碉堡 → 不進 MVP。

保留：雙路、經濟、3 種兵、砲塔、前哨、AI v1、結算、觸控、replay。這些是「Twinfront」之所以成立的底線。

如果 W6 效能未達：

- 先降渲染負載（DPR、粒子、裝飾、更新頻率），不改模擬與相剋。
- 再降場上單位上限（例如每方 24），並在文件記錄；不要假裝 60 單位已達標。
- 若低階 Windows 內顯仍不可玩，考慮把該機型移到「不支援」並更新 DEC-03；不要用 M1 的數據代表低階機。

## 7. 風險

| ID | 風險 | 機率／影響 | 觸發訊號 | 應對 | 檢視點 |
|---|---|---|---|---|---|
| R-01 | 範圍對 part-time 人力太大 | 高／高 | W4 仍無端到端；issue 長期堆積 | 啟動 cut line；每週只維持 1–2 個進行中工作流 | 每週 |
| R-02 | 觸控節奏太忙或理解不足 | 中／高 | 誤觸多、無協助下單率低、局長失控 | 暫停／慢速、減少同時決策、先修 UI 再重測 | W2 |
| R-03 | 先破前哨造成雪球 | 中／高 | 首座前哨歸屬與勝負高度相關 | 分離補給與開路效果；調獎勵、前哨耐久、AI 回防或地圖 | W2、W6 |
| R-04 | 低階裝置掉幀 | 中／高 | 低階 Windows p95 超標；iPad 發熱 | 降視覺負載、降上限、分開記錄裝置；不改規則 | W2、W6 |
| R-05 | 試玩者招募不足 | 中／中 | W4 前少於 5 人排定 | W2 開始招募；準備備取名單；用遠端與現場混合 | W2、W4 |
| R-06 | 美術可讀性不足 | 中／中 | 灰階或色盲模擬下無法辨識 | placeholder 先測輪廓；建立可讀性檢查清單 | M1、M3 |
| R-07 | 內容／IP 爭議 | 低／高 | 真實標誌、裝備名、血腥或仇恨符號 | 架空陣營、原創圖示、內容政策、上架前審查 | 每次素材 PR |
| R-08 | 公開／私人資訊外洩 | 低／高 | 內網主機名、私人 repo、個資進 public | PR 檢查清單；公開前 diff 審閱；敏感內容留私人區 | 每次 release |
| R-09 | 平台規則漂移（Roblox） | 高／中 | 年齡、費用、審核條件變更 | 研究筆記標日期；決策前重查；不把平台細節寫進承諾 | M4 |
| R-10 | 文件漂移 | 中／中 | 同一規則三份文件不一致 | 單一來源規則；里程碑同步；ADR 與 DEC 交叉引用 | 每個里程碑 |

## 8. 現在就能開始

不需要等 W2 拍板：

- 量測現有裝置與舊原型，建立分開的 baseline。
- 畫無素材灰盒：雙路、總部、前哨、四種兵、砲塔。
- 定 Command／Event／Snapshot／Replay schema。
- 做一個可重播的 smoke fixture：開局、下單、擊破前哨、終局。
- 招募 5–8 名試玩者，先排 W2 與 W6 的時段。
- 寫一頁玩家輪廓假設與訪談問題，為 DEC-01 準備。

## 9. 這份文件怎麼改

- 里程碑與日期：在里程碑 review 後更新；不要每週改日期來「看起來準時」。
- 範圍：P0 變更要連到 DEC-06；P1／非目標變更要在 game-design 同步。
- 風險：新增風險要寫觸發訊號與檢視點；沒有的風險不要列。
- 對外承諾：只有【已決】的項目可以寫成承諾；其餘用【暫定】、【假設】、【待決】。
